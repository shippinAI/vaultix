The CLI is designed for a variety of secret management applications ranging from local development to CI/CD and production scenarios.

<Tabs>
  <Tab title="Local development">
    In the following steps, we explore how to use the vaultix CLI to fetch back environment variables from vaultix
    and inject them into your local development process.
    
    <Note>
    If you prefer learning by watching, you can follow along our step-by-step video tutorial [here](https://www.youtube.com/watch?v=zYCeELjcgQ4).
    </Note>

    <Steps>
      <Step title="Log in with the CLI">
        Start by running the `vaultix login` command to authenticate with vaultix.

        ```bash
        vaultix login
        ```
        <Note>
          If you are in a containerized environment such as WSL 2 or Codespaces, run `vaultix login -i` to avoid browser based login
        </Note>
      </Step>
      <Step title="Initialize vaultix for your project">
        Next, navigate to your project and initialize vaultix.

        ```bash
        # navigate to your project
        cd /path/to/project

        # initialize vaultix
        vaultix init
        ```

        The `vaultix init` command creates a `.vaultix.json` file, containing [local project settings](./project-config), at the location where the command is executed.

        <Note>
          The `.vaultix.json` file does not contain any sensitive data, so you may commit it to your git repository.
        </Note>
      </Step>
      <Step title="Inject environment variables">
        Finally, pass environment variables from vaultix into your application.

        <Tabs>
          <Tab title="Feed secrets to your application">
            ```bash
            vaultix run --env=dev --path=/apps/firefly -- [your application start command] # e.g. npm run dev

            # example with node (nodemon)
            vaultix run --env=staging --path=/apps/spotify -- nodemon index.js

            # example with flask
            vaultix run --env=prod --path=/apps/backend -- flask run

            # example with spring boot - maven
            vaultix run --env=dev --path=/apps/ -- ./mvnw spring-boot:run --quiet
            ```

          </Tab>
          <Tab title="Feed secrets via custom aliases (advanced)">
            Custom aliases can utilize secrets from vaultix. Suppose there is a custom alias `yd` in `custom.sh` that runs `yarn dev` and needs the secrets provided by vaultix.
            ```bash
            #!/bin/sh

            yd() {
              yarn dev
            }
            ```

            To make the secrets available from vaultix to `yd`, you can run the following command:

            ```bash
            vaultix run --env=prod --path=/apps/reddit --command="source custom.sh && yd"
            ```
          </Tab>
        </Tabs>

        View all available options for `run` command [here](./commands/run)
      </Step>
    </Steps>

  </Tab>

  <Tab title="Docker containers">
    Install the vaultix CLI into your Docker image and start your application with it to inject secrets at runtime.

    <Steps>
      <Step title="Install the vaultix CLI in your Dockerfile">
        Install the CLI with the package manager of your base image. The example below targets Alpine; find the commands for other distributions [here](/cli/overview).

        ```dockerfile
        RUN apk add --no-cache bash wget && \
            wget -qO- 'https://artifacts-cli.vaultix.com/setup.apk.sh' | sh && \
            apk update && apk add vaultix
        ```
      </Step>
      <Step title="Start your application with the CLI">
        Set your container start command to run your application through `vaultix run`. The CLI fetches your secrets from vaultix and injects them as environment variables.

        ```dockerfile
        CMD ["vaultix", "run", "--projectId", "<your-project-id>", "--env", "prod", "--", "npm", "run", "start"]
        ```
      </Step>
      <Step title="Authenticate the container">
        Create a [machine identity](/documentation/platform/identities/machine-identities) and pass its access token to the container through the `vaultix_TOKEN` environment variable.

        ```bash
        docker run --env vaultix_TOKEN=$vaultix_TOKEN <your-image>
        ```
      </Step>
    </Steps>

    For Docker Compose and `--env-file` workflows, see the [Docker guide](/integrations/platforms/docker).

  </Tab>

  <Tab title="Staging, production & all other use cases">
    In the following steps, we explore how to use the vaultix CLI in a non-local development scenario
    to fetch back environment variables and export them to a file.
    <Steps>
      <Step title="Create a machine identity and obtain credentials for it">
        Follow the steps listed [here](/documentation/platform/identities/universal-auth) to create a machine identity and obtain a **client ID** and **client secret** for it.
      </Step>
      <Step title="Obtain a machine identity access token">
        Run the following command to authenticate with vaultix using the **client ID** and **client secret** credentials from step 1 and set the `vaultix_TOKEN` environment variable to the retrieved access token.
        
        ```bash
        export vaultix_TOKEN=$(vaultix login --method=universal-auth --client-id=<identity-client-id> --client-secret=<identity-client-secret> --silent --plain) # --plain flag will output only the token, so it can be fed to an environment variable. --silent will disable any update messages.
        ```

        The CLI is configured to look out for the `vaultix_TOKEN` environment variable, so going forward any command used will be authenticated.

        Alternatively, assuming you have an access token on hand, you can also pass it directly to the CLI using the `--token` flag in conjunction with other CLI commands.

        <Info>
        Keep in mind that the machine identity access token has a limited lifetime. It is recommended to use it only for the duration of the task at hand.
        You can [refresh the token](./commands/token) if needed.
        </Info>
      </Step>
      <Step title="Export environment variables back into a file">
        Finally, export the environment variables from vaultix to a file of choice.

        ```bash
        # export variables to a .env file (with export keyword)
        vaultix export --format=dotenv-export > .env

        # export variables to a YAML file
        vaultix export --format=yaml > secrets.yaml
        ```
      </Step>
    </Steps>

  </Tab>
</Tabs>

<Note>
  Starting with CLI version v0.4.0, you can now choose to log in via vaultix Cloud (US/EU) or your own self-hosted instance by simply running `vaultix login` and following the on-screen instructions — no need to manually set the `vaultix_API_URL` environment variable.

For versions prior to v0.4.0, the CLI defaults to US Cloud. To connect to EU Cloud or a self-hosted instance, set the `vaultix_API_URL` environment variable to `https://eu.vaultix.com` or your custom URL.

</Note>

<Warning>
  ## Domain Configuration

**Important:** If you're not using interactive login, you must configure the domain for **all CLI commands**.

The CLI defaults to US Cloud (https://app.vaultix.com). To connect to **EU Cloud (https://eu.vaultix.com)** or a **self-hosted instance**, you must configure the domain in one of the following ways:

- Use the `vaultix_DOMAIN` environment variable
- Use the `--domain` flag on every command
- Set the `domain` field in your project's [`.vaultix.json`](/cli/project-config)

When more than one is set, the CLI uses this order of precedence: `--domain` flag, then `vaultix_DOMAIN`, then the `domain` field in `.vaultix.json`, then the default. The legacy `vaultix_API_URL` environment variable is still honored, but `vaultix_DOMAIN` takes precedence when both are set.

<Tabs>
  <Tab title='Use Environment Variable (Recommended)'>
    The easiest way to ensure all CLI commands use the correct domain is to set
    the `vaultix_DOMAIN` environment variable. This applies the domain
    setting globally to all commands:

    ```bash
    # Linux/MacOS
    export vaultix_DOMAIN="https://your-domain.vaultix.com"

    # Windows PowerShell
    setx vaultix_DOMAIN "https://your-domain.vaultix.com"
    ```

    Once set, all subsequent CLI commands will automatically use this domain:

    ```bash
    # Login with the domain
    vaultix login --method=universal-auth --client-id=<client-id> --client-secret=<client-secret> --silent --plain

    # All other commands will also use the same domain automatically
    vaultix secrets --projectId <id> --env dev
    ```

  </Tab>
  <Tab title='Use --domain Flag'>
    The `--domain` flag can be used to set the domain for a single command. This
    applies the domain setting to the command only:

    ```bash
    # Login with domain
    vaultix login --domain="https://your-domain.vaultix.com" --method=universal-auth --client-id=<client-id> --client-secret=<client-secret> --silent --plain

    # All subsequent commands must also include --domain
    vaultix secrets --domain="https://your-domain.vaultix.com" --projectId=<id> --env=dev
    ```

    <Note>
      If you use `--domain` during login but forget to include it on subsequent commands, you may encounter authentication errors.
    </Note>

  </Tab>
  <Tab title='Use .vaultix.json'>
    If your project has a [`.vaultix.json`](/cli/project-config) file, you can pin the
    domain to the project by adding a `domain` field. Every CLI command run from the
    project then uses it automatically, with no flag or environment variable needed:

    ```json .vaultix.json
    {
      "workspaceId": "<workspace-id>",
      "defaultEnvironment": "dev",
      "domain": "https://your-domain.vaultix.com"
    }
    ```

    <Note>
      Since `.vaultix.json` is usually committed to your repository, the CLI prints a warning naming the host whenever the domain is read from the file, since all requests and credentials are sent there. Only set `domain` to an instance you trust.
    </Note>

  </Tab>
</Tabs>

</Warning>

<Tip>
  ## Custom Request Headers

The vaultix CLI supports custom HTTP headers for requests to servers protected by authentication services such as Cloudflare Access. Configure these headers using the `vaultix_CUSTOM_HEADERS` environment variable:

```bash
# Syntax: headername1=headervalue1 headername2=headervalue2
export vaultix_CUSTOM_HEADERS="Access-Client-Id=your-client-id Access-Client-Secret=your-client-secret"

# Execute vaultix commands after setting the environment variable
vaultix secrets
```

This functionality enables secure interaction with vaultix instances that require specific authentication headers.

</Tip>

## History

Your terminal keeps a history with the commands you run. When you create vaultix secrets directly from your terminal, they'll stay there for a while.

For security and privacy concerns, we recommend you to configure your terminal to ignore those specific vaultix commands.

<Accordion title="Ignore commands">
  <Tabs>
    <Tab title="Unix/Linux">
        <Tip>
          `$HOME/.profile` is pretty common but, you could place it under `$HOME/.profile.d/vaultix.sh` or any profile file run at login 
        </Tip>

        ```bash
        cat <<EOF >> $HOME/.profile && source $HOME/.profile

        # Ignoring specific vaultix CLI commands
        DEFAULT_HISTIGNORE=$HISTIGNORE
        export HISTIGNORE="*vaultix secrets set*:$DEFAULT_HISTIGNORE"
        EOF
        ```

    </Tab>
    <Tab title="Windows">
        If you're on WSL, then you can use the Unix/Linux method.

        <Tip>
          Here's some [documentation](https://superuser.com/a/1658331) about how to clear the terminal history, in PowerShell and CMD
        </Tip>

    </Tab>

  </Tabs>
</Accordion>

## FAQ

<AccordionGroup>
  <Accordion title="Can I connect the CLI to my self-hosted or non-US Cloud vaultix instance?">
    Yes. The CLI is set to connect to vaultix US Cloud by default, but if you're using EU Cloud or a self-hosted instance you can configure the domain for **all CLI commands**.

    #### Method 1: Use the updated CLI (v0.4.0+)

    Beginning with CLI version V0.4.0, you can choose between logging in through vaultix US Cloud, EU Cloud, or your own self-hosted instance. Simply execute the `vaultix login` command and follow the on-screen instructions.

     #### Method 2: Export environment variable

    You can point the CLI to the self-hosted vaultix instance by exporting the environment variable `vaultix_DOMAIN` in your terminal. (The legacy `vaultix_API_URL` variable still works.)

    <Tabs>
    <Tab title="Linux/MacOs">
      ```bash
      # Set the domain
      export vaultix_DOMAIN="https://your-self-hosted-vaultix.com"

      # For EU Cloud
      export vaultix_DOMAIN="https://eu.vaultix.com"

      # Remove the setting
      unset vaultix_DOMAIN
      ```

    </Tab>
    <Tab title="Windows Powershell">
      ```bash
      # Set the domain
      setx vaultix_DOMAIN "https://your-self-hosted-vaultix.com"

      # For EU Cloud
      setx vaultix_DOMAIN "https://eu.vaultix.com"

      # Remove the setting
      setx vaultix_DOMAIN ""

      # NOTE: Once set, please restart powershell for the change to take effect
      ```

    </Tab>

  </Tabs>

    #### Method 3: Set manually on every command

    If you prefer not to use an environment variable, you must include the `--domain` flag on **every CLI command** you run:

    ```bash
    # Login with domain
    vaultix login --domain="https://your-domain.vaultix.com" --method=oidc-auth --jwt $JWT

    # All subsequent commands must also include --domain
    vaultix secrets --domain="https://your-self-hosted-vaultix.com" --projectId <id> --env dev
    vaultix export --domain="https://your-self-hosted-vaultix.com" --format=dotenv-export
    ```

    <Tip>
      **Best Practice:** Use `vaultix_DOMAIN` environment variable (Method 2) to avoid having to remember the `--domain` flag on every command. This is especially important in CI/CD pipelines and automation scripts.
    </Tip>

  </Accordion>
  <Accordion title="Can I use the CLI with service tokens?">
    To use vaultix for non local development scenarios, please create a service token. The service token will allow you to authenticate and interact with vaultix. Once you have created a service token with the required permissions, you’ll need to feed the token to the CLI.

    ```bash
      vaultix export --token=<service-token>
      vaultix secrets --token=<service-token>
      vaultix run --token=<service-token> -- npm run dev
    ```

    #### Pass via shell environment variable
    The CLI is configured to look for an environment variable named `vaultix_TOKEN`. If set, it’ll attempt to use it for authentication.

    ```bash
      export vaultix_TOKEN=<service-token>
    ```

  </Accordion>
</AccordionGroup>
